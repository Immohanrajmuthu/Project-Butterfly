# Author's Intent

Documentation is a product.

It deserves the same care, clarity, and intentional design as the software it describes.

Good documentation reduces uncertainty.

It helps people understand decisions, navigate complexity, and contribute with confidence.

The purpose of this standard is to establish a consistent approach to creating documentation that remains useful throughout the lifetime of a project.

---

# Purpose

Documentation exists to communicate knowledge.

It should answer questions before they become obstacles.

Every document should help someone understand a concept, complete a task, or make a better decision.

Good documentation reduces dependency on tribal knowledge and improves collaboration across teams.

---

# Documentation Doctrine

## Documentation Should Teach, Not Just Describe

Documentation is more than recording information.

Its purpose is to help people understand.

Every document should educate, clarify, and guide rather than simply list facts.

---

# Documentation Principles

## Every Document Has One Purpose

Each document should answer one important question.

Avoid combining multiple unrelated topics into a single document.

Focused documents are easier to understand, maintain, and evolve.

---

## Write for Humans First

Documentation should be understandable by people before it satisfies technical completeness.

Prefer simple language over unnecessary jargon.

Assume readers may be new to the project.

---

## Explain Why Before How

Whenever possible, begin with the reason before describing the implementation.

Understanding purpose improves understanding of implementation.

---

## Keep Documentation Close to the Work

Documentation should live alongside the project it describes.

Avoid storing important knowledge in external tools when it belongs with the source.

Documentation should evolve together with the code.

---

## Examples Improve Understanding

Whenever practical, include examples.

Examples communicate intent faster than lengthy explanations.

Prefer realistic examples over abstract ones.

---

## Keep Information Current

Outdated documentation creates more confusion than missing documentation.

When behavior changes, update the documentation as part of the same change.

Documentation should evolve with the project.

---

## Structure Improves Discoverability

Organize documentation into logical sections.

Use clear headings, meaningful file names, and predictable navigation.

Readers should spend time learning—not searching.

---

## Consistency Builds Confidence

Use a consistent writing style, terminology, and document structure across the project.

Consistency makes documentation easier to read and maintain.

---

# Documentation Guidelines

## README Files

Every major directory should include a README when additional context is beneficial.

A README should explain:

- Purpose
- Contents
- Intended audience
- Relationship to the rest of the project

---

## Standards

Standards should include:

- Author's Intent
- Purpose
- Doctrine
- Principles
- Guidelines
- Examples
- Butterfly Test
- Closing Statement

---

## Charters

Charters should include:

- Architect's Intent
- Philosophy
- Doctrine
- Principles
- Review
- Closing Statement

---

## Guides

Guides should focus on completing specific tasks.

Use step-by-step instructions where appropriate.

Assume readers are learning.

---

## Reference Documentation

Reference documents should prioritize accuracy and completeness.

Avoid opinions unless they are clearly identified as recommendations.

---

# Writing Style

Prefer:

- Short paragraphs
- Active voice
- Clear headings
- Descriptive titles
- Simple language
- Consistent terminology

Avoid:

- Long blocks of text
- Unexplained acronyms
- Ambiguous wording
- Excessive technical jargon
- Duplicate information

---

# Document Lifecycle

Documentation should be treated as a living asset.

When creating a document:

- Define its purpose.
- Review its clarity.
- Publish it with the project.
- Maintain it as the project evolves.
- Archive or remove it when it no longer provides value.

---

# Examples

Good

```
Repository Structure Standard

Purpose:
Define how projects should be organized for clarity and maintainability.
```

Poor

```
Miscellaneous Notes

Contains various project information.
```

The first communicates purpose.

The second creates uncertainty.

---

# The Butterfly Test 🦋

Before publishing documentation, ask:

✓ Does this document answer one important question?

✓ Is its purpose immediately clear?

✓ Can a new contributor understand it?

✓ Does it explain why before how?

✓ Are examples provided where helpful?

✓ Is the information accurate and current?

✓ Does it align with the Constitution, Charters, and Standards?

If yes,

the documentation belongs.

---

# Closing Statement

Documentation is not measured by the number of pages it contains.

It is measured by how effectively it helps people understand, learn, and contribute.

Every clear explanation reduces uncertainty.

Every thoughtful example improves understanding.

Every well-written document strengthens the project for future contributors.

That is the documentation standard of Project ButterFly.
